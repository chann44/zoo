---
title: Zoo on Kubernetes
description: Deploy Zoo's control plane from a Helm chart and run Linux sandboxes as Kata pods in your cluster.
---

Kubernetes is an added way to deploy Zoo, for teams that already run clusters. A single
host (`docker compose`) and [zoo-node](/docs/guides/remote-servers/) stay the default and
the fastest path.

On Kubernetes:

- Zoo itself runs as Deployments from a Helm chart (`deploy/helm/zoo`), with Postgres and
  any S3-compatible object storage;
- Linux sandboxes run as pods in the cluster: one pod per sandbox, under the Kata
  Containers RuntimeClass, with a PersistentVolumeClaim for its home and zoo-guest inside;
- macOS and Windows sandboxes still run on Macs and Hyper-V hosts outside the cluster.
  Their zoo-node registers with the same control plane, so one install offers every OS.

## What the chart runs

| Component | What it is | Scaling |
|---|---|---|
| `api` | The API and MCP endpoint (`ZOO_ROLE=api`) | HPA on CPU, 2–10 pods by default |
| `worker` | The job worker: sandbox lifecycle jobs, agent runs, the warm pool, the Discord bot (`ZOO_ROLE=worker`) | 1 pod; more are safe for agent runs |
| `gateway` | The connection gateway (`ZOO_ROLE=gateway`): holds every guest websocket and zoo-node stream | 1 pod, recreated on upgrade |
| `web` | The dashboard | Fixed replicas, or an HPA |
| `egress` | A DaemonSet in the sandbox namespace that enforces each sandbox's network policy on its node | One per node |

**Why a gateway.** A sandbox's guest and a host's zoo-node each hold one long-lived
connection that lands on one process. With several API pods behind a Service, a tool call
can arrive at any pod, so one process — the gateway — holds every connection; the API and
worker pods set `ZOO_GATEWAY` and reach guests and nodes through it. The gateway keeps
nothing of its own: when it restarts, guests and nodes dial it again within seconds.

## Install

The cluster needs: Kubernetes 1.29+, an ingress controller (raise the read/send timeouts
for ingress-nginx — websockets are long-lived), Postgres (the chart creates a
CloudNativePG cluster, or bring your own), shared `/data` storage (ReadWriteMany once
more than one Zoo pod runs), and for sandboxes: [kata-deploy](https://github.com/kata-containers/kata-containers/tree/main/tools/packaging/kata-deploy), nodes with KVM, and a
default StorageClass.

```sh
helm install zoo oci://registry-1.docker.io/chann44/zoo --version <version> \
  --namespace zoo --create-namespace \
  --set ingress.host=zoo.example.com --set ingress.apiHost=api.zoo.example.com \
  --set 'env.ADMIN_EMAILS=you@example.com'
helm test zoo --namespace zoo --logs
```

The chart is published to Docker Hub as an OCI artifact with every release. The settings
that matter most:

| Value | What it does |
|---|---|
| `ingress.host`, `ingress.apiHost`, `ingress.tls` | The public addresses. The API host also takes guests from sandboxes outside the cluster. |
| `database.mode` | `cnpg` (default) creates a CloudNativePG `Cluster`; `external` reads `database.external.existingSecret`. |
| `objectStorage.url`, `.endpoint`, `.existingSecret` | Moves of homes and VM disks between hosts go through it. |
| `secrets.existingSecret`, `secrets.kms`, `externalSecrets.*` | Where `JWT_SECRET` and `ZOO_SECRETS_KEY` come from. |
| `gateway.nodes.endpoint` | `host:port` of the zoo-node load balancer. Required before you add a server with zoo-node. |
| `sandboxes.runtimeClass` | `kata` by default. `runc` runs plain containers on clusters without KVM, with weaker isolation. |
| `sandboxes.storageClass`, `.homeSize`, `.snapshotClass` | The sandboxes' home claims, and CSI snapshots of them. |
| `metrics.serviceMonitor.enabled` | Prometheus Operator scraping of every Zoo pod's `/metrics` (port 9464). |
| `env` | Any setting from the [configuration reference](/docs/reference/configuration/), for every Zoo pod. |

Zoo pods migrate the database as they start, under a Postgres advisory lock, so pods
starting together take turns. Secrets can be generated by the chart (kept even on
uninstall, since losing `ZOO_SECRETS_KEY` loses every stored secret), read from your own
secret, or filled by the External Secrets Operator; with `secrets.kms` the workspace data
keys are wrapped by AWS, GCP or Vault KMS and the pods' identity reaches it — no key
stored in the cluster.

## Sandboxes on Kubernetes

Set `ZOO_KUBERNETES_NAMESPACE` (the chart does) and the Linux sandboxes Zoo runs on "this
machine" become pods in that namespace. Servers added under Servers keep working as
before.

| | How it works |
|---|---|
| Pod | `zoo-sandbox-<id>`, under the RuntimeClass (`kata`), with 2 GiB of memory and 2 CPUs (limits), as on Docker. `NET_RAW` is dropped, privilege escalation is off. |
| Home | The claim `zoo-home-<id>`; an init container seeds it from the image. Stopping deletes the pod and keeps the claim. |
| Guest | zoo-guest dials the gateway's Service; without it, calls fall back to the pods/exec API, which also covers root commands. |
| Desktop | The pod's noVNC port (6080) at the pod's address; from outside the cluster, desktops go through the guest's tunnel. |
| Snapshots | CSI VolumeSnapshots with `sandboxes.snapshotClass`, else a copy by a helper pod on the sandbox's node. |
| Warm pool | Pooled pods wait with every process but init stopped (`SIGSTOP`); a claim wakes one in well under a second. |

### Network

Two layers. The baseline is a NetworkPolicy from the chart: sandboxes reach DNS, the
gateway and the internet, but not `sandboxes.networkPolicy.blockedCIDRs` (cloud metadata
by default) or each other; it needs a CNI that enforces NetworkPolicy. On top, each
sandbox's own policy is enforced by the egress DaemonSet with nftables and a filtering
proxy on the host — root inside the sandbox can't change it. Cilium with eBPF host
routing bypasses the host's netfilter: set `bpf.hostLegacyRouting=true` there.

### Requirements check

`helm test <release>` runs the requirements check: Zoo's access to the namespace, the
RuntimeClass and the ready nodes it can schedule onto, **KVM on those nodes**, the
StorageClass, the egress daemon on every sandbox node, and — with the probe — a pod under
the RuntimeClass on every node, which proves the runtime (and for Kata, KVM) works there.

Kata needs KVM: bare metal, or cloud VMs with nested virtualization (GCE with it enabled,
Azure Dv3/Ev3 and newer, AWS `*.metal` or families that support it). Clusters without KVM
can run `sandboxes.runtimeClass=runc`.

## Limits

- **One gateway.** While it restarts (seconds), tool calls through guests wait or fail,
  and nodes reconnect on their own.
- **Shared `/data`** must be ReadWriteMany once more than one Zoo pod runs.
- **runc sandboxes are less confined than on Docker** — the runtime's default seccomp
  profile rather than Zoo's stricter one and its AppArmor profile. Under Kata, each
  sandbox is its own VM and that doesn't apply.
- **No pids limit per sandbox.** Kubernetes sets pid limits per node, in the kubelet's
  `podPidsLimit`.

:::note
We evaluated [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox)
before writing our own. It fits the same problem; Zoo uses plain Pods and claims because
it already reconciles sandboxes with its job queue, the warm pool maps better onto pods
that boot under their final identity, plain Pods need nothing in the cluster beyond Kata,
and it wouldn't do more for isolation. We'll look again when its API reaches v1 and
hibernation lands.
:::
